INVEST (Качество пользовательских историй) I Independent — Независимая (не зависит от других) N Negotiable — Обсуждаемая (можно уточнить) V Valuable — Ценная (дает пользу бизнесу) E Estimable — Оцениваемая (понятные трудозатраты) S Small — Маленькая (входит в спринт) T Testable — Тестируемая (есть критерии приемки) 🗺️ USM (User Story Mapping): Карта пользовательских историй — визуализация бэклога по оси «Шаги пользователя» (горизонталь) и «Приоритет/версии» (вертикаль). 🚀 MVP (Minimum Viable Product): Минимальная версия продукта с достаточной ценностью для первых пользователей 5. Методология, Модели и Философия 📐 Методология Принципы и правила работы (Scrum, Kanban). 🧩 Модель разработки Абстрактное упрощение процесса (Waterfall, V-Model, Spiral). 🏗️ Фреймворк Готовое решение/каркас для разработки (Django, React, Spring). 🌱 Философия Базовые ценности и подходы (Agile, Lean, DevOps). 1. Классические модели 💧 Водопадная модель (Waterfall) Последовательно 1. Анализ 2. Требования 3. Проектирование 4. Разработка 5. Тестирование 6. Ввод и поддержка (Нельзя вернуться на шаг назад) ✅ V-Model (верификация/валидация) Левая сторона Бизнес-требования → Функциональные → Архитектура → Системы → Компонентов Правая сторона (тестирование каждого уровня) 2. Базовые понятия циклов 🧩 Инкремент Завершенная и полезная часть продукта (готовый кусок функционала). 🔄 Итерация Цикл (временной отрезок) внутри проекта, после которого делают инкремент. 3. Гибкие и быстрые подходы (RAD / Спираль) ⚡ RAD (Rapid Application Development) Быстрая разработка приложений. Главный выбор: * 1 Скорость + Качество * 2 Низкая Стоимость + Качество * 3 Скорость + Низкая Стоимость (Классический треугольник: выбирай 2 из 3) 🌀 Спиральная модель Каждый виток (цикл): Анализ рисков → Разработка → План следующего витка. Подходит для крупных проектов с высокими рисками. 4. Философия AGILE (Манифест) 👤 Люди важнее процессов 📦 Продукт важнее документации 🤝 Позиция клиента важнее контракта 🔄 Готовность к изменениям важнее следования плану 5. Фреймворк SCRUM 📆 Планирование (Sprint Planning) — что делаем в спринте ☀️ Дейли (Daily Scrum) — 15 минут на синхронизацию 🔍 Ретроспектива — как мы работали, что улучшить 6. Экстремальное программирование (XP) 🧑‍🤝‍🧑 Парное программирование (два разработчика за одним экраном) 🏢 Заказчик рядом (On-site Customer) 🎯 Игра в планирование (приоритеты задач) 🧪 Разработка через тестирование (TDD — сначала тест, потом код) 7. LSD (Lean Software Development) Бережливая разработка — убираем всё, что не приносит ценности клиенту. Минимизация потерь (лишний код, долгие совещания, перепроизводство фич). 8. Стратегия тестирования ⬅️ Shift Left Testing — «Сдвиг влево» (тестирование начинается как можно раньше, на этапе требований/проектирования, чтобы находить баги до написания кода). ➡️ Shift Right Testing — тестирование в production (мониторинг, A/B тесты на реальных пользователях). 9. ⚠️ Реалии рынка (Антипаттерн) 🚀 ХХП — «Хуяк-хуяк и в продакшн» (Минуя тесты, документацию и здравый смысл. Используется, когда дедлайн вчера). 👤 Аккаунт-менеджер 📈 Продакт 📋 Проджект 📊 Бизнес-аналитик ⚙️ Системный аналитик 🏗️ Архитектор ✍️ Техпис 💻 Разработчик 🔄 ДевОпс 🧪 Тестировщик 🧑‍💼 Тимлид 1. Система контроля версий (Git) 📂 Репозиторий Папка с проектом (локальная .git или удалённая на GitHub/GitLab). 📍 Коммит Точка (слепок) изменений с хешем и сообщением. 🌿 Ветка (Branch) Последовательность коммитов (изолированная линия разработки). Базовые команды Git (ключевые) Команда Что делает git commit -m "fix" Создает коммит (точку сохранения) git log --oneline Показывает историю коммитов (сокращённо) git push origin main Отправляет коммиты в удалённый репозиторий git merge feature Сливает ветку feature в текущую git pull Скачивает изменения с удалённого репо и сливает (fetch + merge) git checkout -b new Создаёт и переключает на новую ветку (с - switch/create) git branch -vv Показывает все ветки и их привязку к удалённым (вв — очень подробно) 2. DevOps (Development & Operations) 🐳 Docker Контейнеризация — упаковка приложения со всеми зависимостями. ☸️ Kubernetes (k8s) Оркестрация контейнеров (автоматическое развертывание, масштабирование). ⚙️ Jenkins CI/CD сервер — автоматизирует сборку, тесты и деплой. 3. CI/CD (Непрерывная интеграция и доставка) 🔄 CI (Continuous Integration) Непрерывная интеграция — каждый коммит автоматически собирается и тестируется. 🚀 CD (Continuous Delivery / Deployment) Непрерывная поставка / развертывание — автоматическая выкатка на окружения (вплоть до Prod). 4. Окружения (Environments) Среда (Environment) — это инфраструктура: физические серверы, виртуалки, сетевые устройства, облака. 🛠️ Dev — Создание (разработчики пишут код) 👀 Demo — Можно потрогать (показать заказчику) 🧪 Test — Тестирование (авто- и ручное) 🏁 Stage — Предпрод (максимально похож на бой) 🌍 Prod — Production (видят все пользователи) 5. Объектно-Ориентированное Программирование (ООП) 📐 Классы — Шаблоны для создания объектов (чертёж) 📦 Объекты — Структуры с данными (атрибутами) и методами (поведением) 🏷️ Атрибуты — Характеристики (поля) объекта (цвет, размер, имя) ⚡ Методы — Поведение объекта (функции, которые он может выполнять) Принципы ООП (4 столпа) 🔒 Инкапсуляция — информация хранится внутри объекта (скрываем детали). 🎭 Абстракция — выделяем общие атрибуты и методы, убирая лишнее. 🧬 Наследование — создание новых классов на основе существующих (родитель → потомок). 🔄 Полиморфизм — один и тот же метод работает по-разному для разных классов. 6. UX/UI Дизайн 😊 UX (User Experience) — Опыт пользователя от взаимодействия с системой (удобство, эмоции). 🎨 UI (User Interface) — Как выглядит продукт (кнопки, цвета, шрифты). Юзабилити (Usability) — оцениваем по: * Удобство — легко ли пользователю достигать целей. * Интуитивность — понятно ли с первого взгляда. * Нет ошибок — система предотвращает или прощает ошибки. * Удовлетворение — приятно ли пользоваться. Инструменты и подходы (Figma и не только) 📱 Адаптивность — подстраивается под экран (мобилка/планшет/ПК). ⚡ Отзывчивость — моментальная реакция на действия пользователя. 🎮 Геймификация — игровые механики (бонусы, уровни). 🏢 Внутренняя — для сотрудников компании (ERP, CRM). 🌐 Внешняя — для клиентов и пользователей (сайты, приложения). 7. Web: Домены, DNS, IP, URL 🌐 Домен — Человекочитаемое имя сайта (example.com). 📖 DNS (Domain Name System) — Переводит домен в IP-адрес (как телефонная книга). 🔢 IP-адрес — Уникальный сетевой адрес устройства (192.168.1.1). 🔗 URL (Uniform Resource Locator) — Полный адрес ресурса: https://domain.com/path?param=1. 1. Модели сетевого взаимодействия 📚 OSI (Open Systems Connection) 🌐 TCP/IP (Transmission Control Protocol / Internet Protocol) Практический стек протоколов (4 уровня). Сравнение уровней OSI и TCP/IP Уровень OSI TCP/IP Что делает / Примеры Прикладной (7) Прикладной Общение приложений: HTTP, SMTP (почта), FTP (файлы) Сессионный (6) / Представительский (5) Управление сессией, шифрование, кодирование данных Транспортный (4) Транспортный Доставка данных: TCP (надёжный) и UDP (быстрый) Сетевой (3) Межсетевой Маршрутизация между сетями (IP-адресация) Канальный (2) / Физический (1) Канальный (сетевой доступ) Передача по физической среде: Ethernet, Wi-Fi, оптоволокно 💻 Клиент — устройство, которое запрашивает информацию. 🖥️ Сервер — устройство, которое отдаёт информацию. 📡 LAN — Локальная сеть (офис, дом). 🌍 WAN — Глобальная сеть (Интернет). 🔐 Безопасность / Шифрование: данные шифруются на сессионном уровне (SSL/TLS), чтобы никто не мог прочитать трафик 2. Базы данных СУБД (Система Управления Базами Данных) — программное обеспечение для хранения, изменения и обработки данных (PostgreSQL, MySQL, Oracle, MongoDB). 3. Аутентификация и токены 🔑 Токен аутентификации — цифровой ключ, подтверждающий личность. 📜 JWT (JSON Web Token) — компактный токен в формате JSON, содержит данные пользователя и подпись. ⏳ Короткоживущий токен — живёт 5–30 минут (Access Token), повышает безопасность. 🔗 OAuth — протокол, позволяющий войти через соцсеть (Google, VK) без передачи пароля. 4. Архитектура приложений 🏛️ Монолит Вся логика внутри одной кодовой базы (единый .jar/.exe). ✅ Просто развернуть, ❌ трудно масштабировать. 🧩 Микросервисы Приложение разбито на множество независимых сервисов. ✅ Масштабируются по отдельности, ❌ сложное сетевое взаимодействие. 🗄️ Database Per Service — у каждого микросервиса своя база данных (изоляция данных). 5. API (Application Programming Interface) API — это правила и способы обмена данными между системами. 🔍 Аналогия: официант в ресторане — вы ему заказ (запрос), он приносит блюдо (ответ). 🔗 Endpoint — это конкретный URL-адресат, по которому стучатся к API (например, /api/users). Типы API (по доступности) 🌍 Открытые (Public) — доступны всем, нужен API-ключ для связи между серверами (не путать с токеном пользователя). 🤝 Партнёрские — доступны только проверенным компаниям-партнёрам. 🏢 Внутренние — только внутри компании, не торчат наружу. 🧩 Составные (Composite) — один API, который агрегирует данные из нескольких других API. 6. REST API (Representational State Transfer) Передача самоописываемого состояния — архитектурный стиль для веб-сервисов. 6 принципов REST (must have): * Клиент-серверная архитектура — разделение ответственности (UI отдельно, данные отдельно). * Отсутствие состояния (Stateless) — каждый запрос содержит всю информацию для выполнения (сессии не хранятся на сервере). * Кэшируемость — ответы должны маркироваться как кэшируемые или нет. * Единообразие интерфейса — стандартные методы: GET, POST, PUT, DELETE. * Слои (Layered System) — клиент не знает, работает ли он напрямую с сервером или через прокси. * Код по требованию (Code on Demand) — опционально: сервер может передавать клиенту исполняемый код (например, JavaScript). 7. Форматы передачи данных 📄 XML (EXtensible Markup Language) Строгий, многословный формат. Используется в SOAP и старых корпоративных системах. John 📦 JSON (JavaScript Object Notation) Лёгкий, человекочитаемый формат. Используется в 95% современных REST API. {"user": {"name": "John"}} 8. SOAP API (Simple Object Access Protocol) ⚠️ SOAP — это строгий протокол, использующий XML и сложные стандарты (WS-Security). Часто используется в банках и госструктурах. ✍️ Отличие от REST: REST — это стиль (архитектура), а SOAP — это именно протокол с жёсткими правилами. 1. GraphQL 📊 GraphQL — язык запросов к API, разработанный Facebook. Отличие от REST: клиент сам решает, какие поля ему нужны (не перекачивает лишние данные). Пример: запрос { user(id: 1) { name, email } } — вернёт только имя и почту. 2. Протокол HTTP и адресация 🌐 HTTP (HyperText Transfer Protocol) — протокол передачи гипертекста (основа веба). 🔗 URI (Uniform Resource Identifier) — идентификатор ресурса (общее понятие). 📍 URL (Uniform Resource Locator) — конкретный адрес ресурса (частный случай URI). Структура URL: http:// (протокол) + vk.ru (доменное имя) = протокол + домен — это и есть URI/URL. 3. Структура HTTP-запроса GET /api/users HTTP/1.1 ← Start Line (Метод + URI + Версия) Host: vk.ru ← Заголовки (Headers) Authorization: Bearer token123 ← Заголовки Content-Type: application/json ← Заголовки   ← Пустая строка (Empty Line) — разделитель { "name": "John" } ← Тело (Body) — опционально 🚀 Start Line / Request Line — метод, URI, версия HTTP. 📋 Headers — метаданные (тип контента, авторизация, куки). ⬜ Empty Line — разделяет заголовки и тело. 📦 Body — данные запроса (POST/PUT/PATCH). 4. CRUD (Create, Read, Update, Delete) Действие HTTP Метод SQL Create (Создать) POST INSERT Read (Прочитать) GET SELECT Update (Обновить) PUT (полная замена) / PATCH (частичная) UPDATE Delete (Удалить) DELETE DELETE 5. HTTP Методы (полный список) 🔍 GET — запрос данных (без тела). 📄 HEAD — только заголовки (без тела). 🔧 OPTIONS — спрашивает, какие методы поддерживает сервер. ➕ POST — создаёт ресурс (не идемпотентный). 🔄 PUT — полная замена ресурса (идемпотентный). ✏️ PATCH — частичное изменение (не всегда идемпотентный). 🗑️ DELETE — удаляет ресурс (идемпотентный). 6. Идемпотентность и безопасность методов 🔄 Идемпотентный — метод, который можно вызвать несколько раз с одинаковым результатом. Пример: PUT /users/1 — первый раз создаст, второй раз просто перезапишет (состояние то же). 🛡️ Безопасный — метод не изменяет ресурс на сервере (только читает). GET, HEAD, OPTIONS — безопасные. Таблица идемпотентности методов Метод Идемпотентный? Безопасный? Есть тело? HTTP Коды ответа (полный список по вашим записям) 1xx — Информационные 102 Processing — сервер принял запрос, но ещё не завершил обработку (используется для WebDAV). 2xx — Успех 200 OK — запрос успешно выполнен. 201 Created — ресурс создан (обычно POST). 3xx — Перенаправление 301 Moved Permanently — ресурс навсегда перемещён на новый URL. 302 Found — временное перенаправление. 4xx — Ошибка клиента 400 Bad Request — сервер не понимает запрос (невалидные данные). 401 Unauthorized — требуется аутентификация. 403 Forbidden — доступ запрещён (аутентификация есть, но прав нет). 404 Not Found — ресурс не найден. 405 Method Not Allowed — метод не поддерживается для этого ресурса. 5xx — Ошибка сервера 500 Internal Server Error — общая ошибка сервера. 501 Not Implemented — сервер не поддерживает нужную функциональность. 503 Service Unavailable — сервер временно перегружен или на обслуживании. 505 HTTP Version Not Supported — сервер не поддерживает версию HTTP. 8. Базы данных (БД) База данных — организованное хранилище, позволяющее хранить, изменять, извлекать и удалять данные. 📊 Реляционные (SQL) Табличная структура, строгие схемы, связи между таблицами. Примеры: PostgreSQL, MySQL, Oracle, MS SQL 📦 Нереляционные (NoSQL) Гибкие структуры (документы, ключ-значение, графы). Примеры: MongoDB, Redis, Cassandra, Neo4j Ключи в реляционных БД 🔑 Первичный ключ (Primary Key) — уникальный идентификатор записи в таблице. Пример: user_id = 1 🔗 Внешний ключ (Foreign Key) — столбец, который ссылается на первичный ключ другой таблицы (для связи). Пример: order.user_id → users.user_id 9. Нормализация БД 🧩 Нормализация — это декомпозиция (разбиение) БД на логические части для устранения дублирования и аномалий. Цель: правильное проектирование структуры данных. 📌 1НФ (каждое поле атомарно) → 2НФ (зависит от всего ключа) → 3НФ (нет транзитивных зависимостей). ⚖️ Балансировщик (Load Balancer) — распределяет нагрузку между несколькими серверами БД или приложений для повышения производительности и отказоустойчивости. 1. NoSQL — нереляционные базы данных ⚡ Redis — хранилище ключ-значение в оперативной памяти (in-memory). Используется для кэширования, сессий, очередей. 📄 JSON-документные — хранят данные в виде JSON-документов (MongoDB, CouchDB). 🕸️ Графовые — данные в виде узлов (nodes), рёбер (edges) и свойств (properties). Идеально для соцсетей, рекомендаций (Neo4j, ArangoDB). 📊 Столбцовые (Columnar) — данные хранятся по столбцам, а не по строкам. Отлично для аналитики (HBase, Cassandra, ClickHouse). 🧩 HBase — столбцовая БД на основе Hadoop, используется для больших данных (Big Data). 2. Масштабирование баз данных ✂️ Партицирование (Partitioning) — разбиение одной таблицы на части (горизонтальное/вертикальное) внутри одной БД. 🌍 Шардирование (Sharding) — распределение данных по разным серверам (каждый шард — отдельная БД). 📋 Репликация (Replication) — создание копий БД на разных серверах. ⏳ Асинхронная репликация — сначала запись в оригинал, потом в реплики (быстрее, но есть риск потери данных). 🔒 Синхронная репликация — запись сразу во все реплики (медленнее, но данные надёжнее). 3. SQL (Structured Query Language) 📜 Декларативный язык — мы описываем ЧТО хотим получить, а не КАК это сделать. Популярные СУБД (SQL) 🐬 MySQL 🐘 PostgreSQL 📦 SQLite 🏢 Microsoft SQL Server Императивные языки (в отличие от SQL) 🐍 Python 🟨 JavaScript 4. ACID — свойства транзакций 🔬 Atomicity (Атомарность) — транзакция выполняется целиком или не выполняется вообще (всё или ничего). ⚖️ Consistency (Согласованность) — транзакция переводит БД из одного корректного состояния в другое. 🔒 Isolation (Изоляция) — параллельные транзакции не влияют друг на друга (как будто выполняются по очереди). 💾 Durability (Долговечность) — после фиксации (COMMIT) данные сохраняются даже при сбое. 5. Типы SQL-запросов (4 группы) DDL — Data Definition Language (определение данных) 🏗️ DDL — создание и изменение структуры БД. * CREATE TABLE — создание таблицы * CREATE USER — создание пользователя * ALTER — модификация структуры (добавить/удалить столбец) * DROP — удаление таблицы/БД DML — Data Manipulation Language (изменение данных) ✏️ DML — работа с данными внутри таблиц. * SELECT — выборка данных * INSERT — вставка новых записей * UPDATE — обновление существующих * DELETE — удаление записей * MERGE — слияние (обновить или вставить) DCL — Data Control Language (управление доступом) 🔐 DCL — права доступа. * GRANT — разрешение на операции * REVOKE — отзыв разрешений * DENY — явный запрет TCL — Transaction Control Language (управление транзакциями) 🔄 TCL — управление транзакциями. * BEGIN / COMMIT — объявление и фиксация транзакции * ROLLBACK — откат изменений 6. Брокеры сообщений (Message Brokers) Брокер — посредник между отправителем и получателем сообщений (Kafka, RabbitMQ, ActiveMQ). 📤 Producer (Отправитель) — создаёт и отправляет сообщения в топик. 📥 Consumer (Потребитель) — читает сообщения из топика. 📂 Topic (Топик) — тема с разделами (категория сообщений). 🧩 Partitions (Разделы) — распределение данных внутри топика для параллельной обработки. 📍 Offset — уникальный номер сообщения внутри раздела. 7. Логирование (Logging) Логирование — запись событий: сбоев, ошибок, подозрительных действий (вид взлома), информационных сообщений. Уровни логирования (от критичного к детальному) FATAL Тотальный сбой, приложение падает ERROR Некорректная работа, но приложение живёт WARN Предупреждение (потенциальная проблема) INFO Информация о работе приложения (старт, остановка, бизнес-события) DEBUG Детальная информация для разработчиков (старт/пауза методов) TRACE Мельчайшая запись процесса (почти каждая строчка кода) 8. Кэш и хранение состояния 📄 Кэш — копии страниц/данных для быстрого доступа (хранятся в оперативной памяти). Примеры: Redis, Memcached, CDN 🍪 Куки (Cookies) — служебные файлы, хранящиеся локально в браузере пользователя. 🔐 Сессия (Session) — данные о пользователе, хранящиеся на сервере (обычно в Redis или БД). Куки хранят только ID сессии, а сами данные — на сервере. 1. Принципы тестирования (7 принципов) 🐛 1. Наличие дефектов — тестирование показывает наличие дефектов, а не их отсутствие. ⏰ 2. Раннее тестирование — начинать как можно раньше (Shift Left). 📊 3. Скопление дефектов — 80% ошибок сосредоточено в 20% модулей (принцип Парето). 🧪 4. Парадокс пестицида — если повторять одни и те же тесты, они перестают находить новые баги. Нужно встряхивать тестовую базу. 🎯 5. Контекст тестирования — тестирование зависит от контекста (веб-приложение тестируем иначе, чем банковскую систему). ❌ 6. Заблуждение об отсутствии ошибок — если система стабильна, но неудобна пользователям — это плохо. Отсутствие багов ≠ успех. 2. Уровни тестирования (по объёму) 🧩 Модульные (Unit) — тестирование отдельных функций/методов. 🔗 Интеграционные — проверка взаимодействия между модулями. 🏛️ Системные — тестирование всей системы целиком. ✅ Приемочные (Acceptance) — проверка соответствия требованиям заказчика. 3. QA и QC — в чём разница? 🛡️ QA (Quality Assurance) — обеспечение качества. Процессы, стандарты, предотвращение ошибок (проактивный подход). 🔍 QC (Quality Control) — контроль качества. Поиск ошибок в готовом продукте (реактивный подход). 4. Что такое БАГ? БАГ (Bug) — это любой недостаток / ошибка / действие, которое приводит к: * Ошибке (неправильный результат) * Сбою (временная проблема) * Отказу (постоянный сбой) * Недостатку памяти и другим проблемам Фактический Результат отклоняется от Ожидаемого Результата. 5. Верификация и Валидация (главное отличие) 📋 Верификация (Verification) — проверка соответствия формальным требованиям (документации, спецификации). 👤 Валидация (Validation) — проверка соответствия требованиям пользователя (реальным нуждам). 🎯 Классический пример (ОСЁЛ vs КОНЬ): 🐴 Релиз — ОСЁЛ (непарнокопытное с 4 ногами), а нужен был КОНЬ. ✅ Верификация пройдена — осёл соответствует документации (4 ноги, копыта). ❌ Валидация НЕ пройдена — пользователь хотел коня, а получил осла. 6. STLC (Software Testing Life Cycle) Жизненный цикл тестирования: 1. Общее планирование 2. Уточнение критериев 3. Уточнение стратегии 4. Чеклисты 5. Тест-кейсы 6. Анализ результатов 7. Тестовая документация 📋 Тест-план — общий план тестирования 📊 Test Strategy — стратегия тестирования ✅ Check list — список проверок (без шагов) 📝 Test case — детальный тест-кейс с шагами 📂 Test suite — набор тест-кейсов 🐛 Баг-репорт — отчёт об ошибке 📈 Test Report — отчёт о результатах 🔗 Traceability Matrix — матрица трассировки (связь требований ↔ тестов ↔ багов) 8. Виды тестирования (все классификации) По цели (функциональное vs нефункциональное) ⚡ Функциональное — проверка того, ЧТО делает система. Альфа / Бета / Модульное / Интеграционное / Системное / Приемочное ⚙️ Нефункциональное — проверка того, КАК система работает. Нагрузочное / Производительность / Стабильность / Отказоустойчивость / Стресс / Масштабируемость / Безопасность / Совместимость По важности (глубине) 🔥 Дымовое (Smoke) — проверка критической функциональности (сборка вообще работает?). 🛤️ Критического пути (Sanity) — проверка основных бизнес-сценариев. 🧪 Расширенное (Regression) — полная проверка, чтобы новые изменения не сломали старый функционал. По характеру 😊 Позитивное — проверка на корректных данных (всё должно работать). 😈 Негативное — проверка на некорректных данных (система должна корректно обрабатывать ошибки). По доступу к коду 🔓 Белый ящик (White Box) — тестировщик видит код, знает внутреннюю структуру. ⬛ Чёрный ящик (Black Box) — тестировщик не видит код, проверяет только входы и выходы. 10. Специальные виды тестирования 😊 Юзабилити (Usability) — насколько удобно пользователям. ♿ Accessibility — тестирование доступности (для людей с ограниченными возможностями). ⏳ Availability — доступность системы (истекший SSL, низкая скорость интернета). 🌍 Интернационализация — проверка, что продукт можно адаптировать под разные страны. 🗺️ Локализация — проверка конкретной адаптации (перевод, валюта, дата).
